# Связанный анализ, прогноз и дообучение по факту

Статус: экспериментальный контур `coupled-multimodal-hydrostatic-v1`.
Он объединяет две существующие ветви без двойного усвоения одних наблюдений.

## 1. Вычислительный тракт

```text
доступные к T0 наблюдения
  -> MultimodalWeatherModel.analysis_state
  -> [N, K=8, H_a] анализ
  -> LatentToPressureBridge
  -> [N, 37, H_f] начальное состояние
  -> HydrostaticFlowProfileModel / Joint surface head
  -> +3 ... +72 ч
  -> архив прогноза с checkpoint_id и evidence ids
```

Multimodal/Adaptive используется как оператор анализа. Его собственный 72-часовой decoder не нужен в этом тракте. Joint/Hydrostatic используется как прогнозная динамика. Его прежний ingest GHCNh/IGRA не вызывается повторно: иначе одинаковые наблюдения вошли бы в состояние два раза.

`LatentToPressureBridge` выполняет cross-attention от 37 запросов гидростатического фонового состояния к `K` латентным позициям анализа. Поправка ограничена gate-механизмом. Новый bridge инициализируется как точный no-op и должен пройти отдельное обучение до научной оценки coupled-прогноза.

## 2. Быстрое и медленное дообучение

После выпуска прогноз не меняется. Когда приходит факт для уже прошедшего valid time, система сначала рассчитывает ошибку и регистрирует новую версию целевого примера. Дальше действует два темпа.

**Fast loop** обновляет bridge и прогнозные `dynamic/tendency/head/surface_head`. Multimodal-энкодеры заморожены. Это снижает риск того, что несколько свежих случаев разрушат оператор ассимиляции.

**Slow loop** запускается реже после накопления принятых fast-шагов. Он может разморозить `encoder/processor/satellite_bank/source_fusion` и bridge. Для него нужен отдельный guard-набор и более строгая проверка.

## 3. Почему модель не обучается на каждом одиночном наблюдении

Один новый факт слишком шумный и локальный. Базовая политика ждёт минимум 32 новых train-примера и берёт не более 128 за один шаг. На каждый новый пример добавляются до трёх исторических replay-примеров. Replay выбирается детерминированно и стратифицируется по месяцам, чтобы уменьшить забывание сезонов.

Эти числа заданы в `configs/coupled_online_learning.json` как исследовательские defaults. Они не являются доказанным оптимумом.

## 4. Защита от деградации

Существующие `CampaignStore` и `StepTrainer` остаются источником истины.

1. После физического QC и проверки provenance поступившая цель получает immutable-событие `fact_admitted`; одного `usage_plan` недостаточно.
2. Факт становится train-примером только если неизменяемая split-политика назначила ему роль `train`.
3. `validation`, `test` и `guard` не могут попасть в `usage_plan`: это защищено схемой SQLite и `StepTrainer`.
4. Перед update считается метрика текущей опубликованной модели на фиксированном guard-наборе.
5. Выполняется ровно один optimizer step кандидата.
6. Те же guard-примеры оцениваются повторно.
7. Кандидат публикуется только при улучшении primary metric и отсутствии недопустимой деградации guardrail-метрик.
8. Если кандидат отклонён, callback поднимает `CandidateRejected`. `StepTrainer` не публикует generation и не создаёт `training_event`.
9. Новая сессия `StepTrainer` восстанавливает модель и optimizer из последнего авторитетного checkpoint.

Таким образом, «самообучение» не означает безусловное изменение боевых весов после каждого факта.

## 5. Ошибка прогноза

`masked_error_metrics` считает `RMSE`, `MAE`, `bias`, `abs_bias` только по реально пришедшим и физически допущенным целям. Пропуск не превращается в ноль. Для величин с разными единицами можно передать фиксированный scale, полученный только из обучающей части.

Для реальной эксплуатации оценку нужно хранить отдельно по lead time, переменной, уровню давления, региону/режиму и источнику факта. Глобальное среднее не должно скрывать локальную деградацию.

## 6. Причинность

У каждого архивного прогноза должны сохраняться:

- issue time и valid time;
- checkpoint generation;
- точный набор evidence ids, доступных к issue time;
- версии норм, сетки и модели;
- hash исходных прогнозных массивов;
- версия фактического target asset и время его доступности.

Новый факт используется как target, но не задним числом как input старого прогноза. После его прихода он может войти во вход следующего анализа.

## 7. API кода

`global_weather.coupled.CoupledAnalysisForecastModel` — единый вычислительный граф двух ветвей.

`global_weather.continuous.feedback.ReplayPlanner` — формирует пакет из свежих train-use и исторического replay.

`GuardedOnlineLearner` — выполняет кандидатный шаг через существующий `StepTrainer`, оценивает guard-набор и публикует только прошедший кандидат.

Пример интеграции:

```python
coupled.set_trainable("fast")
optimizer = torch.optim.AdamW(
    [p for p in coupled.parameters() if p.requires_grad], lr=1e-5, weight_decay=1e-4
)
planner = ReplayPlanner(store, policy)
batch = planner.plan()
if batch["status"] == "ready":
    result = learner.attempt(batch["use_ids"], cursor={"feedback_cycle": cycle_id})
```

`batch_loss` и `evaluate` передаются исполнителю как доверенные функции проекта. Они должны читать только зарегистрированные артефакты и не выполнять сетевые запросы внутри optimizer step.

## 8. Что ещё требуется до operational

Новый код создаёт архитектурный bridge и безопасный feedback executor, но сам по себе не доказывает качество прогноза. Перед operational promotion нужны реальное paired-обучение bridge, многосезонный hindcast, независимый guard/test, сравнение с persistence/NWP/раздельными ветвями, стресс-тест на пропуски источников и измеренная стоимость Mesh-8 rollout.
