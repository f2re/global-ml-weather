# Непрерывное обучение: оператор выбирает только даты

Идентификатор: `GLOBAL-WEATHER-CONTINUOUS-1`.
Постановка оператора: 5 октября 2026 года.
Проверенная база: `e68f0c5f8f24f6c762c77aee8c0c032a9719c713`.
Статус: план следующей реализации, не описание уже работающего нового конвейера.

Документ заменяет пользовательский сценарий `GLOBAL-WEATHER-AUTO-1`.
Существующий автономный эксперимент остаётся проверяемой основой и временным расширенным режимом.
[Аудит текущего сценария](audits/2026-10-05-continuous-training-flow.md) фиксирует причины изменения.
[Контракт исполнителя](../agents/CONTINUOUS_TRAINING_CONTRACT.md) задаёт обязательные ограничения.
[Машиночитаемый план](../configs/continuous_training_roadmap.json) содержит зависимости и критерии приёмки.

## 1. Пользовательский результат

Основной экран содержит начальную дату, конечную дату и кнопку «Обучать».
Оператор не выбирает станции, каналы, размер блока, устройство, эпохи и доли выборки при каждом запуске.
Диапазон относится к срокам выпуска обучающих примеров в UTC.
Конечный день включается целиком; внутри программы используются полуоткрытые интервалы.

Первое нажатие создаёт постоянную модель и задание подготовки выбранного периода.
Следующее нажатие с другими датами продолжает ту же модель, если сохраняется совместимость.
Повторный диапазон не означает автоматического повторного обучения на прежних примерах.

После запуска сразу открывается карта обеспеченности данными.
Первый пригодный блок начинает обучение автоматически после обязательных проверок и подготовки норм.
Повторная кнопка подтверждения всего плана не требуется.
Оператор может поставить процесс на паузу, пока просматривает карту.

Проверка всего многолетнего каталога не должна задерживать первый пригодный блок.
Дальние периоды получают предварительные статусы; ближайшие проходят полную проверку файлов.
Граница достоверно проверенного периода видна на экране.

### Настройки, которые выполняются один раз

Доступы, разрешение сети, локальное хранилище и пределы ресурсов относятся к установке комплекса.
Сервер предлагает безопасные пределы по фактическому оборудованию и свободному месту.
Они сохраняются и не запрашиваются повторно для каждого диапазона.
Увеличение расходов или выход за согласованные пределы требует отдельного разрешения.

CDS требует токен и принятие условий соответствующих наборов владельцем аккаунта [S2].
GPTL может требовать вход, разрешения S3 и зарегистрированного клиента OAuth [S3].
Комплекс объясняет необходимое действие, проверяет результат и возобновляет заблокированные зависимости.
Он не принимает юридические условия и не регистрирует внешнего клиента от имени пользователя без поручения.

## 2. Постоянная модель вместо отдельной модели на каждый запуск

Ввести сущность «программа обучения» с постоянным `campaign_id`.
В неё входят версия модели, история диапазонов, задания, данные, контрольные точки и независимые оценки.
Запрос дат создаёт `request_id`, но не сбрасывает модель и оптимизатор.

| Сущность | Назначение |
|---|---|
| `campaign` | Постоянная модель, неизменяемые научные параметры и политика обучения |
| `request` | Порученный диапазон дат и ссылка на программу обучения |
| `source_asset` | Конкретная версия файла или сообщения поставщика |
| `logical_block` | Устойчивая часть временного диапазона, независимая от размера загрузки |
| `work_slice` | Изменяемый физический фрагмент загрузки, декодирования или вычисления |
| `sample` | Выпуск, целевой горизонт, состав входов и ссылки на их версии |
| `split_assignment` | Постоянная роль примера: обучение, проверка, итоговый тест или защитный интервал |
| `training_event` | Зафиксированное применение конкретных примеров к весам |
| `checkpoint_generation` | Полное согласованное состояние модели и позиции выполнения |
| `remediation_task` | Ошибка зависимости, автоматическое решение и необходимое действие оператора |
| `evaluation` | Метрики с точной версией весов, данными и периодом их независимости |

Архитектура, сетка, вертикаль и атмосферные нормы фиксируются в версии модели.
Изменение дат не меняет эти параметры.
Изменение архитектуры или несовместимой нормировки создаёт явно связанную дочернюю версию.
Исходная обученная версия сохраняется.

## 3. Разбиение многолетнего периода

Убрать ограничение 366 суток на уровне программы обучения.
Ограничивать нужно отдельный запрос поставщику, рабочую очередь, память и занимаемый кэш.
Пример 2000–2005 означает даты `2000-01-01` — `2005-12-31`, то есть шесть календарных лет.

Предлагаемая исходная гранулярность логического блока — сутки UTC.
При открытии длинного периода интерфейс агрегирует сутки в месяцы и годы.
Загрузчик вправе делить сутки на сроки, каналы, области или группы станций.
Укрупнение сетевого запроса не меняет принадлежность обучающих примеров.

У каждого выпуска есть единственный владеющий блок по времени выпуска.
История наблюдений берётся из предыдущих 12 часов.
Цели запрашиваются до конца прогнозного горизонта, включая соседние даты.
Вспомогательные даты не становятся дополнительными обучающими выпусками вне порученного диапазона.
Общие файлы соседних блоков скачиваются и декодируются один раз.

Проверка норм может потребовать несколько обучающих блоков до первого шага оптимизатора.
Эти блоки явно обозначаются как подготовка фиксированной нормировки.
Нельзя обучать с временными нормами, а затем незаметно заменять их постоянными.

### Ограниченный конвейер

Разделить исполнителей проверки каталога, загрузки, подготовки и обучения.
Модель изменяет только один обучающий исполнитель.
Поколение аренды проверяется при фиксации шага; устаревший исполнитель не может публиковать состояние после передачи владения.
Предзагрузка по умолчанию ограничена двумя ближайшими пригодными блоками.
При заполнении кэша подготовка приостанавливается, не уничтожая контрольные точки.

Состояние плана хранится в SQLite, а не в одном многолетнем JSON-массиве.
Пагинация обязательна для файлов, примеров, блоков и элементов карты обеспеченности.
Блочные массивы читаются по необходимым времени, переменной и уровню.
Нельзя загружать весь диапазон в RAM или повторно объединять его в один NPZ.

## 4. Автоматическое обнаружение и проверка источников

Ввести единый контракт провайдера:
`discover → inspect_access → enumerate → acquire → decode → quality_check → admit`.
Каждый этап возвращает типизированный результат, доказательство, время проверки и срок актуальности.
Сетевой запрос никогда не исполняется внутри шага оптимизатора.

| Источник | Автоматическое поведение | Условие использования |
|---|---|---|
| GHCNh | Найти существующие файлы выбранных лет, прочитать каталог, получить пригодные наблюдения без ручного списка станций | Проверены схема, единицы, координаты, качество, дубликаты и временная поддержка |
| ERA5 | Рассчитать полный набор целей, осадков и статики, разбить запросы по лимитам CDS | Все обязательные цели каждого выпуска прошли проверку покрытия |
| Аэрология | Найти подходящий исторический источник, например IGRA, и собственный декодер профиля | Нет подмены скачанного архива готовым адаптером; до реализации статус «адаптер не готов» |
| Арктика-М | Сначала проверить доступный каталог arktika-worker, затем недостающие объекты GPTL | Подтверждены прибор, физический канал, калибровка, геометрия и время |
| Электро-Л | Обнаружить коллекции и физические каналы GPTL, проверить объектный доступ | Собственная приборная идентичность; никакого переименования в Арктику-М |
| Другие спутники | Подключать зарегистрированным адаптером по мере его реального допуска | Отсутствие адаптера не обозначается как отсутствие спутниковых наблюдений |

### GHCNh без ручного выбора станций

Не использовать восемь станций или первые 128 записей как скрытую глобальную выборку.
По умолчанию учитывать все доступные пригодные станции выбранного периода.
Физические задания обрабатывают их ограниченными пакетами.
Если ресурсов недостаточно, конвейер замедляется или ожидает место, а не молча удаляет станции.

Для больших объёмов сравнить PSV и Parquet на одних реальных исходных записях [S1].
Parquet допускается после проверки соответствия величин, кодов качества и пропусков.
Предпочитать чтение требуемых столбцов и временных фрагментов, если формат и сервер это поддерживают.
Годовой файл станции не скачивается повторно для каждого суточного блока.

### ERA5 и долговременные задания

Сохранить отдельные запросы мгновенных полей, часовых осадков и статики.
Ключ запроса включает набор, переменные, сроки, уровни, сетку и версию преобразования.
Сохранить идентификатор удалённого задания сразу после его получения.
Перезапуск сначала опрашивает существующее задание, а не повторяет дорогую заявку.

Для этого оценить `ecmwf-datastores-client`: он поддерживает метаданные и управление заданиями [S2].
Закрепить проверенный выпуск; не переходить автоматически на непроверенную последнюю версию.
Действующий `cdsapi` остаётся совместимым путём, а не объявляется устаревшим без основания.
Переключение пути получения не должно менять физический контракт целей.

### Арктика-М и arktika-worker

Подключение к существующему каталогу сохраняется один раз.
Поддержать документированный локальный API и чтение разрешённых экспортов без изменения поставщика.
Сначала проверить уже скачанные сцены, паспорта, контрольные суммы и статус обработки.
Отсутствующие зависимости получают задания подготовки, а не требуют ручного поиска каждого TIFF.

Не изменять базу arktika-worker напрямую и не запускать его обработчик через произвольную команду браузера.
При необходимости записи использовать отдельный узкий согласованный API и контракт версии.
Самовольная загрузка Python-модулей из указанного оператором каталога запрещена.
Установленный поставщик проверяется отдельно от закреплённого исходного коммита.

### Электро-Л

Пользователь не вводит идентификаторы коллекций и каналов при запуске обучения.
Система сопоставляет метаданные каталога с версионированным реестром приборов.
Неоднозначное сопоставление создаёт задачу обновления адаптера, а не предполагаемую калибровку.
Полная пагинация и успешная проверка фильтра обязательны для утверждения об отсутствии сцен.

Открытый каталог `roscosmos-opendata` содержит данные Электро-Л, Арктики-М и Метеора-М [S3].
Это не подтверждает наличие каждого срока, уровня обработки или права чтения конкретного объекта.
Сначала проверяется каталог, затем чтение объекта, затем физическая пригодность.

## 5. Карта обеспеченности и обучение на ней

Столбцы показывают время, строки — источники и при необходимости приборы.
При выборе ячейки открываются конкретные сроки, файлы, пропуски, причины и действия.
Графика строится только из состояния backend и сохранённых результатов проверок.
Цвет дублируется значком и текстом; неизвестное значение не заменяется нулём.

| Измерение состояния | Значения |
|---|---|
| Каталог | Не проверено; перечислено полностью; перечислено частично; подтверждённо отсутствует; вне периода источника |
| Доступ | Публичный; проверен; нужен вход; истёк; нет прав; условия не приняты; временная ошибка |
| Подготовка | Ожидает; загружается; скачано; проверяется; пригодно; частично пригодно; карантин |
| Обучение | Не запланировано; ожидает; обучается; частично зафиксировано; полностью зафиксировано; намеренно отложено |

Для каждой ячейки показывать число ожидаемых, найденных, проверенных и пригодных сроков, когда известны соответствующие знаменатели.
Отдельно показывать полученные байты, число станций, каналы и фактическое пространственное покрытие.
«Один файл читается» не означает «месяц обеспечен данными».
Доля покрытия приборной области не называется глобальной обеспеченностью атмосферы.

Прогресс обучения определяется зафиксированными примерами и шагами, а не количеством скачанных файлов.
Частично обученный блок не закрашивается как полностью завершённый.
При агрегации месяца сохраняются доли всех состояний и признаки ошибок.
Неизвестные и ещё не проверенные периоды остаются видимыми.

Верхняя строка показывает период, текущий блок, устройство, последний сохранённый шаг и общую историю модели.
Уведомления появляются при переходе состояния, а не при каждом повторе запроса.
Подробный журнал доступен по раскрытию; обычный экран не требует чтения технических сообщений.

## 6. Нет данных, нет доступа и нет адаптера — разные ситуации

| Ситуация | Автоматическое действие | Когда требуется человек |
|---|---|---|
| Поставщик временно недоступен | Ограниченные повторы с задержкой, затем отложенное повторение; готовые блоки остаются доступными | Только после устойчивого отказа с понятной диагностикой |
| Токен истёк | Обновить разрешённым refresh-механизмом и повторить запрос | Если обновление отклонено, показать «Войти снова» |
| Условия CDS не приняты | Сохранить заявку и показать ссылку на конкретный набор | Принятие условий владельцем аккаунта |
| Нет прав S3 при доступном STAC | Отдельно проверить объектный доступ, сохранить код отказа | Настройка разрешений; не подменять отказ пустым каталогом |
| Источник отсутствует в этот период | Отметить неприменимость, использовать остальные допустимые модальности | Не требуется для автоматического режима |
| Есть снимок, но нет калибровки | Попытаться получить подтверждённый продукт или метаданные; иначе карантин | Только недостающая внешняя процедура, которую нельзя выполнить автоматически |
| Есть разрыв обязательных целей | Докачать недостающее; при устойчивом разрыве отложить затронутые выпуски | Изменение обязательного набора целей требует явного решения |
| Недостаточно места | Остановить предзагрузку, удалить только разрешённый воспроизводимый кэш | Увеличение лимита или выбор другого хранилища |
| Ошибка CUDA или нехватка VRAM | Сохранить последнюю подтверждённую точку; уменьшить физический пакет в рамках политики | Смена устройства после начала требует явной миграции и нового протокола |
| Поменялся формат источника | Остановить соответствующий декодер, сохранить вход и диагностические признаки | Обновление адаптера и его приёмка |

Обязательность определяется профилем этапа, а не наличием кнопки в интерфейсе.
В автоматическом базовом режиме спутники желательны, но их отсутствие не выдумывает измерения.
В заданном этапе спутникового дообучения отсутствие спутников блокирует этот этап.
Недопустимо молча назвать повторное приземное обучение спутниковым.

Последующие независимые блоки могут готовиться при ошибке предыдущего.
Если политика разрешает пропустить временной разрыв, порядок фактического обучения записывается явно.
Позднее заполнение разрыва использует журнал примеров и не повторяет уже зафиксированную работу.

## 7. Сохранение состояния и восстановление

Сохранять не только веса, но и оптимизатор, расписание скорости обучения, состояние масштабирования и генераторы случайных чисел [S4].
Дополнительно сохранять номер шага, порядок примеров, позицию внутри блока, выполненные накопления градиента и версии входов.
Граница сохранения по умолчанию — каждый завершённый шаг оптимизатора.
При накоплении градиента безопасная граница находится после применения накопленного шага.

Для публикации нужны две проверяемые генерации: текущая и предыдущая.
Их отображение как A/B допустимо, но перезаписывать единственную пригодную генерацию запрещено.
Хранить файлы генераций неизменяемыми; менять только ссылки на них.
Всегда удерживать текущую и предыдущую генерации, выбранные лучшие веса и закреплённые границы этапов.
Старые незакреплённые файлы удаляет отдельный проверяемый сборщик после фиксации новых генераций.
Метаданные поколений, хэши и журнал применения примеров сохраняются независимо от удаления старого файла весов.
Нельзя накапливать полные файлы каждого шага без ограниченной политики хранения.

### Транзакция фиксации шага

1. Вычислить шаг на конкретном наборе примеров, не отмечая их обученными в базе.
2. Сохранить новую генерацию во временный каталог; проверить состав, конечность тензоров и контрольные суммы.
3. Выполнить `fsync` файлов, опубликовать каталог атомарным переименованием и синхронизировать родительский каталог.
4. В одной транзакции SQLite записать генерацию, использованные примеры, курсор и новый указатель текущего состояния.
5. После фиксации транзакции уведомить интерфейс об обученных данных.

Файловая публикация и транзакция SQLite не образуют одну общую атомарную операцию.
Поэтому база является источником истины для текущего указателя, а неопубликованные в базе генерации считаются незавершёнными.
В WAL использовать подтверждённую конфигурацию долговечности и `synchronous=FULL` [S5].
База SQLite/WAL размещается на локальной файловой системе, не на сетевом томе [S5].
Резервное копирование должно учитывать базу, WAL и связанные контрольные точки согласованно.
Повреждение уже зафиксированной генерации не позволяет молча перейти на старые веса с новым журналом.
Сначала искать резервную копию именно этой генерации с совпадающими хэшами.
Если доступна только предыдущая, создать восстановительную ветвь и согласованно восстановить её курсор и журнал применений.
Более поздние события сохраняются как отменённые повреждением; соответствующие примеры снова ставятся в очередь.
Интерфейс отдельно сообщает потерю подтверждённого состояния и используемую точку восстановления.

| Момент сбоя | Восстановление |
|---|---|
| Во время загрузки | Продолжить согласованный объект или получить заново только повреждённую часть |
| Во время вычисления шага | Вернуть предыдущее сохранённое состояние и повторить незавершённый шаг |
| Во время записи контрольной точки | Игнорировать незавершённую генерацию; текущая и предыдущая остаются пригодными |
| После публикации файлов, до SQLite | Не считать примеры обученными; использовать предыдущую зафиксированную генерацию |
| После SQLite, до обновления интерфейса | Прочитать сохранённый указатель; не повторять зафиксированный шаг |
| После последнего шага блока, до отметки блока | Восстановить завершение блока из журнала использованных примеров |
| После перезапуска сервера | Восстановить аренды исполнителей, курсоры и очередь; автоматически продолжить незавершённое |

Достижимая гарантия — однократное применение каждого зафиксированного события к сохранённой истории модели.
Незавершённое вычисление физически может выполняться повторно после восстановления.
Это не двойное применение градиента, поскольку исходные веса и оптимизатор тоже восстанавливаются.

Гарантия ограничена корректной работой файловой системы, накопителя и механизма синхронизации.
Она не защищает от утраты всего диска без отдельной резервной копии.
Абсолютная доступность внешних архивов не обещается.

## 8. На каких данных модель уже обучалась

Ввести устойчивые идентификаторы примеров, независимые от границ запроса и физического размера блока.
Идентичность учитывает выпуск, горизонт, версию исходных данных, состав модальностей и версию преобразования.
Хэш ZIP, дата файла или название папки по отдельности недостаточны.

Ключ события обучения включает `campaign_id`, `stage_id`, `sample_id` и номер разрешённого прохода.
Разрешённые повторные эпохи и повторение части старых примеров записываются отдельными проходами.
Защита от случайного повторного обучения не должна запрещать запланированную оптимизацию.

Повторное измерение внутри одного выпуска удаляется по источнику, идентификатору и ревизии.
Использование того же измерения в соседнем причинно допустимом окне — другой случай.
Не смешивать эту логику с журналом использования обучающих примеров.

При расширении периода сравнить новый план с журналом.
Существующие события показываются как уже выполненные; новые интервалы добавляются к очереди.
Изменённая версия источника образует новые данные, а не незаметную замену старого файла.
Правило повторного обучения на исправленных данных задаётся версией политики и отражается в отчёте.

## 9. Обучение без спутников, затем спутниковое дообучение

По умолчанию доступные и допущенные модальности определяются для каждого периода автоматически.
Граница 2024 года не зашивается как дата появления спутниковых данных.
Она может быть выбранной оператором границей этапа, но не доказательством наличия архива.

Дополнительный, необязательный сценарий — «Добавить этап».
У него те же даты и назначение: базовое обучение или спутниковое дообучение.
Станции, коллекции, каналы и размер блока всё равно не выбираются вручную.

Пример последовательности:

| Этап | Даты | Поведение |
|---|---|---|
| Базовый | 2000-01-01 — 2005-12-31 | Обучение на доступных приземных и допущенных профильных наблюдениях; собственные допустимые нормы |
| Продолжение | 2006-01-01 — 2023-12-31 | Те же веса, оптимизатор, атмосферные нормы и журнал; без обнуления истории |
| Спутниковый | 2024-01-01 — 2025-12-31 | Проверка реального архива Арктики-М и Электро-Л, отдельные нормы каналов, затем дообучение |

### Добавление ветви модели

Предпочтительна архитектура с зарегистрированными отключаемыми модальностями и маской их доступности.
Появление нового прибора требует отдельного физического контракта и не подменяется нулевыми значениями.
Недостающий вход должен иметь маску отсутствия, а не физическую яркостную температуру 0 K.

Если существующая модель не содержит нужного кодировщика, создать дочернюю версию с отчётом миграции.
Все совместимые атмосферные параметры переносятся точно и проверяются по именам, формам и значениям.
Состояние оптимизатора переносится только для совпадающих параметров.
Новые параметры инициализируются отдельно и явно; молчаливое использование `strict=False` запрещено.

Атмосферные нормы остаются прежними, а нормы нового прибора рассчитываются по его обучающей части.
Приборные нормы не выдаются за действовавшие до их формирования.
Смена приборной нормировки не должна ошибочно выглядеть совместимым продолжением прежней контрольной точки.

Для защиты от забывания оценивать отдельно приземный режим и режим с доступными спутниками.
Ввести проверяемое отключение модальностей и воспроизведение части старых обучающих примеров.
Долю повторения выбирать по проверочным данным, не по итоговому тесту.
Повторение отмечается как намеренное и не меняет постоянные роли контрольных примеров.

## 10. Постоянные выборки и фиксированные нормы

Нельзя заново делить весь диапазон по долям при каждом новом запросе.
Иначе вчерашний итоговый тест может завтра попасть в обучение.
Принадлежность к выборке сохраняется на уровне абсолютного временного интервала и версии политики.

До расчёта норм зарезервировать обучающие, проверочные, тестовые интервалы и защитные промежутки.
Их назначение не зависит от того, есть ли в момент запуска удобные наблюдения.
Пропуски не дают права автоматически превратить контрольный интервал в обучающий.

Для каждого выпуска проверять непересечение фактической истории входов и горизонта целей разных ролей.
Размер защитного промежутка учитывает 12 часов входа, до 72 часов цели и дополнительные зависимости продукта.
Простого запрета одинаковых дат или совпадающих идентификаторов файлов недостаточно.

Новый журнал кампании требует своего валидатора временных ролей.
Нельзя удалить строгую проверку старого `PreparedDataset._check_splits()` ради прохождения нового сценария.
Обычные подготовленные эксперименты сохраняют прежние ограничения.

### Начальные периоды до 2015 года

Включённые статистики GraphCast используют период до 2015 года.
Поэтому они не годятся для заявления независимого исторического теста за 2000–2005 годы.
Это подтверждается текущим паспортом файлов и проверкой `assert_independent_test`.

Автоматически выбирать опубликованные статистики только с допустимым и доказанным периодом.
Если таких статистик нет, подготовить фиксированные нормы из зарезервированных обучающих блоков ERA5.
Сохранить происхождение, периоды, единицы, контрольные суммы и метод расчёта.
При нулевой дисперсии расширить обучающий набор в разрешённом периоде, а не подставлять единицу.

Нормы не пересчитываются на каждом блоке и не меняются при расширении диапазона.
Добавление более ранних дат допускает обучение совместимыми весами, но не создаёт независимости от будущих норм.
Такие контрольные оценки помечаются непригодными для исторического вывода.
Для строгого ретроспективного эксперимента требуется отдельная версия с допустимой нормировкой и переобучением.

### Оценка при продолжении

Для каждой оценки фиксировать точку весов и все временные интервалы, повлиявшие на её обучение и выбор.
Прошлый тест, просмотренный и использованный для решений, нельзя бесконечно называть новым независимым тестом.
Вести журнал использования контрольных результатов и отдельную независимую отложенную выборку.
При проверке на следующем временном блоке сначала сохранить прогноз и оценку прежних весов, затем разрешать последующее обучение.
Итоговые резервные примеры не обучаются даже после такой оценки.

## 11. Выбор устройства и ресурсы

CUDA имеет приоритет в режиме `auto`.
До первого шага проверять не только наличие устройства, но и выполнение необходимых операций, свободную память и конечность контрольного прохода.
Без пригодной CUDA выбирать CPU до начала обучения и показывать причину.

Сетка, вертикаль и состав выходов не уменьшаются молча из-за нехватки VRAM.
Разрешено изменять физическое пакетирование и предзагрузку в пределах закреплённого численного протокола.
Смена точности, устройства или алгоритма накопления оформляется как явное продолжение с новым протоколом.
Не обещать побитовую воспроизводимость разных устройств или недетерминированных операторов.

Лимиты устанавливаются на занимаемое место и живые задания, а не на сумму всех байтов за годы.
Удаление воспроизводимого кэша возможно только после фиксации обучения и проверки зависимостей воспроизведения.
Контрольные точки, нормы, журналы происхождения и резервные контрольные данные не удаляются этим механизмом.

## 12. API и интерфейс

Ниже проектируемые маршруты, отсутствующие в проверенной базе.
Они не считаются реализованными после добавления этого документа.

| Метод и маршрут | Назначение |
|---|---|
| `POST /api/learning/ranges` | Принять только `start_date` и `end_date`; продолжить выбранную постоянную модель |
| `GET /api/learning/state` | Модель, устройство, контрольная точка, стадия и ожидаемые действия |
| `GET /api/learning/coverage` | Карта обеспеченности с масштабом год/месяц/день и пагинацией |
| `GET /api/learning/blocks/{id}` | Реальные доказательства готовности, пропуски и использованные примеры |
| `GET /api/learning/events` | Последовательность событий с курсором возобновления |
| `POST /api/learning/pause` | Пауза на ближайшей безопасной границе |
| `POST /api/learning/resume` | Возобновление сохранённой программы, не создание новых весов |
| `POST /api/learning/tasks/{id}/retry` | Перепроверить исправленную зависимость |
| `POST /api/learning/stages` | Необязательное добавление периода спутникового дообучения |

Сохранить защиту Host, CSRF, локальное размещение и CSP без `unsafe-eval`.
Поток событий должен поддерживать восстановление по номеру последнего события.
Закрытие вкладки и потеря соединения не отменяют серверное задание.
Дублирующий запрос запуска имеет ключ идемпотентности и не создаёт вторую программу.

Первичная конфигурация и обычное обучение должны быть разными экранами.
Расширенные параметры не удаляются, но относятся к версии программы и не мешают основному сценарию.
Встроенная инфографика должна иметь табличное представление для проверки значений и доступности.

## Источники и их назначение

Публичные источники проверены 5 октября 2026 года.
Они подтверждают внешние интерфейсы и базовые требования, но не работоспособность проектируемого конвейера.

- S1: [NOAA GHCNh](https://www.ncei.noaa.gov/products/global-historical-climatology-network-hourly). Форматы и массовый доступ; замена ISD.

- S3: [GPTL API](https://s3.gptl.ru/geoportal-public/pro-guide/v1/index.html). STAC, метеорологические данные, OAuth и S3.
- S4: [PyTorch: полная контрольная точка](https://docs.pytorch.org/tutorials/recipes/recipes/saving_and_loading_a_general_checkpoint.html). Сохранение модели и оптимизатора для продолжения.
- S5: [SQLite: атомарность](https://www.sqlite.org/atomiccommit.html), [WAL](https://www.sqlite.org/wal.html), [synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous). Границы транзакции и долговечности.
